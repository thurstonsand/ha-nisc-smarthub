# Home Assistant integration practice

Research checked against Home Assistant Core tag **2026.9.1**, current developer and HACS documentation, and PyPI metadata on 2026-09-11. This is a recommendation, not an implemented or smoke-tested integration. Repository constraints come from [AGENTS.md](../../../../AGENTS.md), [CONTEXT.md](../../../../CONTEXT.md), [DEV.md](../../../../DEV.md), [mise.toml](../../../../mise.toml), and [pyproject.toml](../../../../pyproject.toml). No dependency installation or production access was performed.

## Verdict and authority

**Core says:** use a config flow, typed config-entry runtime data, a shared update coordinator, and entities that read cached data. Bronze is the admission baseline for new Core integrations; the scale is cumulative. A HACS integration remains in the **Custom** category, not officially Bronze, Silver, Gold, or Platinum merely because it implements the rules. Sources: [Quality Scale](https://developers.home-assistant.io/docs/core/integration-quality-scale/), [fetching data](https://developers.home-assistant.io/docs/integration_fetching_data/), and [runtime-data rule](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/runtime-data/).

**Our call:** adopt all applicable Bronze and Silver rules, plus diagnostics, translations, reconfiguration, and async/typing practices from higher tiers. Use [Opower at 2026.9.1](https://github.com/home-assistant/core/tree/2026.9.1/homeassistant/components/opower) as the structural reference: its [manifest](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/opower/manifest.json) declares `cloud_polling`, `platinum`, and `dependencies: ["recorder"]`; its [coordinator](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/opower/coordinator.py) writes external statistics. Copy its responsibilities, not its utility-specific implementation or exemptions.

## Style and modules

**Core says:** follow PEP 8 and PEP 257, use Ruff formatting, ordered imports and constants, module docstrings, full type annotations, and lazy `%s` logging. Log messages omit terminal periods and never disclose credentials or usernames. Its [2026.9.1 AGENTS.md](https://github.com/home-assistant/core/blob/2026.9.1/AGENTS.md) specifically prefers concrete types, direct access to validated dictionary keys, narrow exception handlers, and comments only for non-obvious constraints. Python 3.14 permits lazy annotations and the new exception syntax; do not add compatibility machinery for older Python. Sources: [style guidelines](https://developers.home-assistant.io/docs/development_guidelines/) and [AGENTS.md](https://github.com/home-assistant/core/blob/2026.9.1/AGENTS.md).

**Core says:** the [component code-review checklist](https://developers.home-assistant.io/docs/creating_component_code_review/) requires pinned manifest requirements and an external PyPI library for API-specific communication, and asks for small, independently reviewable changes. Some older checklist advice, notably `hass.data[DOMAIN]`, is superseded for new config-entry integrations by the explicit [runtime-data rule](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/runtime-data/). Its [review process](https://developers.home-assistant.io/docs/review-process/) emphasizes tests and focused changes. Existing code is not an exemption from current rules.

**Our call:** use a typed, injected async SmartHub client isolated from HA and tariff calculations. Publishing that client separately is the Core-conformant choice. Keeping it bundled initially is a deliberate custom-integration exception, not something Core recommends; settle that packaging choice in the design. Keep mise, uv, hk, and strict basedpyright rather than importing Core's whole development environment. The repo's current Ruff selections are a subset of [Core's pinned Ruff configuration](https://github.com/home-assistant/core/blob/2026.9.1/pyproject.toml#L643), which requires Ruff >=0.16.3 and includes docstring, async, logging, pytest, and many other checks with deliberate exclusions. Harvest the applicable selections and exclusions together rather than enabling every rule or claiming the present scaffold matches Core.

**Core says:** integration code lives under a directory named for its domain; `manifest.json` and `__init__.py` are foundational, while platforms and other modules follow functionality. Shared coordinator/entity patterns belong in common modules. Sources: [file structure](https://developers.home-assistant.io/docs/creating_integration_file_structure/) and [common-modules](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/common-modules/).

**Our call:** retain the HACS-shaped checkout `custom_components/nisc_smarthub/`, containing `__init__.py` for setup/unload/migration, `config_flow.py` for UI flows, `coordinator.py` for fetch/reconcile orchestration, `sensor.py` for cycle-to-date and freshness entities, `const.py`, `diagnostics.py`, `manifest.json`, `strings.json`, and `translations/en.json`. Add separate tariff and statistic-writing modules because those responsibilities exist, not to reproduce a template's file count. Add `entity.py` only if entities genuinely share more than their coordinator. Keep sanitized fixtures and tests outside the installed integration.

## Coordinator, entities, and ownership

**Core says:** instantiate the coordinator with `config_entry=entry`; use `_async_setup` for one-time initialization and `_async_update_data` for shared fetches. Await `async_config_entry_first_refresh()` before forwarding platforms; transient startup failure becomes `ConfigEntryNotReady`, while authentication failure should raise `ConfigEntryAuthFailed` and initiate reauth. Convert expected API errors to `UpdateFailed`; the coordinator already handles common timeout/client failures and logs unavailable/recovered transitions. Use `always_update=False` only when equality on returned data correctly represents observable changes. Sources: [fetching data](https://developers.home-assistant.io/docs/integration_fetching_data/), [test-before-setup](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/test-before-setup/), and [log-when-unavailable](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/log-when-unavailable/).

**Our call:** define a concrete `NiscSmartHubConfigEntry = ConfigEntry[NiscSmartHubCoordinator]` type alias and store the coordinator in `entry.runtime_data`. Follow [Opower setup/unload](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/opower/__init__.py): first refresh, assign runtime data, await `async_forward_entry_setups`, and unload platforms with `async_unload_platforms`. Register integration-owned listener/timer cleanup with the entry lifecycle. One scrape must feed both statistics and sensors; entity properties must never perform network or recorder I/O. Keep each reconcile operation serialized and make repeated imports idempotent. These last two constraints follow our statistics-writing design, not a separate Quality Scale rule.

**Core says:** a coordinator only polls while it has listeners. `CoordinatorEntity` supplies listener lifecycle, non-polling entity behavior, and availability. Specify `PARALLEL_UPDATES = 0` for read-only coordinator-backed sensor platforms because the coordinator owns concurrency. Sources: [fetching data](https://developers.home-assistant.io/docs/integration_fetching_data/) and [parallel-updates](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/parallel-updates/).

**Our call:** statistics ingestion must survive every sensor being disabled. Give the entry an explicit coordinator subscription independent of entity listeners, removed on unload, and test that condition. Do not accidentally make recorder imports depend on whether a user wants the allowance sensor. Choose the polling interval from the utility's publication cadence and rate limits, not the fact that readings are hourly; Core requires an [appropriate polling interval](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/appropriate-polling/), not a particular interval for SmartHub. Freshness must distinguish the last successful fetch from the latest reading timestamp.

**Core says:** use `has_entity_name = True`, stable unique IDs, and `translation_key` for translated entity names. Entity properties return cached values. The entity registry combines integration/platform identity with the entity unique ID; names, mutable addresses, and user-editable labels are not stable identity. Sources: [entity API](https://developers.home-assistant.io/docs/core/entity/), [entity registry](https://developers.home-assistant.io/docs/entity_registry_index/), and [entity-translations](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/entity-translations/). [Opower sensor.py](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/opower/sensor.py) demonstrates frozen, keyword-only description dataclasses and coordinator-backed sensors.

**Our call:** use `SensorEntityDescription` entries with stable metric keys and translation keys; extend the description only for real per-metric behavior. Derive config-entry identity from co-op plus stable account identity, and sensor identities from that identity, service location, meter where relevant, and metric key. Keep external statistic IDs independently stable under `nisc_smarthub:`; they are not entity-registry IDs. Do not change either identity when credentials, rates, names, or billing-cycle settings change. Never put actual account identifiers in examples, tests, logs, or diagnostics.

**Core says:** since 2026.8 a device has exactly one owning config entry and at most one subentry; identifiers/connections are scoped to the config entry and devices no longer merge across integrations. Prefer `self.device_entry` inside an entity; direct lookups use `async_get_device_by_identifier(identifier, entry.entry_id)` or the connection equivalent. Use `config_entry_id`, `config_subentry_id`, and `via_device_id`, not the deprecated plural ownership properties, global lookup, or `via_device`. Sources: [2026.8 ownership announcement and migration examples](https://developers.home-assistant.io/blog/2026/07/21/device-registry-single-config-entry/).

**Our call:** register our own meter/service-location devices through entity device information. Do not attach our config entry to gagata's device or assume that matching meter identifiers merges them. Temporary coexistence at cutover means separate devices, entities, and statistic namespaces.

## Configuration and migration

**Core says:** authenticate/test the connection in the user flow, set a stable flow unique ID, and abort duplicates. Reauth updates the existing entry after checking identity; reconfigure changes required setup data without creating another entry. Use `_get_reauth_entry()` / `_get_reconfigure_entry()`, `async_set_unique_id`, `_abort_if_unique_id_mismatch()`, and `async_update_reload_and_abort` as appropriate. Sources: [config flow](https://developers.home-assistant.io/docs/config_entries_config_flow_handler/), [reauthentication-flow](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/reauthentication-flow/), and [reconfiguration-flow](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/reconfiguration-flow/).

**Core says:** `data` holds required setup information; an [options flow](https://developers.home-assistant.io/docs/config_entries_options_flow_handler/) exposes optional behavior. Use the flow's `self.config_entry`; `OptionsFlowWithReload` supplies automatic reload when appropriate. Required non-authentication settings belong in reconfigure, not an options flow merely because the user might edit them. `VERSION` and `MINOR_VERSION` default to 1; minor changes are backward-compatible, major changes are not. Implement `async_migrate_entry` in `__init__.py`, update using `hass.config_entries.async_update_entry`, and return success only after migration. Source: [config-entry migration](https://developers.home-assistant.io/docs/config_entries_config_flow_handler/#config-entry-migration).

**Our call:** credentials, co-op/account selection, the required rate schedule and dated rate configuration, and configured billing-cycle start belong in entry data. Reauth repairs credentials; reconfigure changes the non-authentication settings while preserving account identity. An options flow is justified only if we introduce a truly optional behavior such as a user-adjustable polling preference. Do not store hourly readings or growing backfill history in config-entry options. Test migration fixtures for each supported persisted schema and reject unsupported future major versions instead of silently rewriting them. Gagata's different domain is a separate cutover, not an `async_migrate_entry` migration.

## Applicable Quality Scale rules

**Core says:** all rules for a tier and its lower tiers must be implemented or have a justified exemption. The authoritative [rule index](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/) links a dedicated page for every rule below. [Opower's quality_scale.yaml](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/opower/quality_scale.yaml) is a useful example of documenting exemptions, not permission to inherit them.

**Our call, Bronze:** apply `appropriate-polling`, `brands`, `common-modules`, `config-flow`, `config-flow-test-coverage`, `dependency-transparency`, `docs-high-level-description`, `docs-installation-instructions`, `docs-removal-instructions`, `entity-unique-id`, `has-entity-name`, `runtime-data`, `test-before-configure`, `test-before-setup`, and `unique-config-entry`. These cover setup, duplicate prevention, identity, module placement, dependency disclosure, and user documentation. [Config-flow coverage](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/config-flow-test-coverage/) includes user, reauth, reconfigure, and any options flows, not only the initial happy path. [Dependency transparency](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/dependency-transparency/) matters particularly for an undocumented portal client. The [brands rule](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/brands/) is Core's branding requirement; HACS also supports integration-local assets as discussed below.

**Our call, Bronze conditional/exempt:** `action-setup` and `docs-actions` are exempt while there are no custom actions; `docs-triggers` and `docs-conditions` are exempt while there are no custom triggers/conditions. Writing statistics to recorder is not a custom service action. [Entity-event-setup](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/entity-event-setup/) has no additional custom work if `CoordinatorEntity` handles all entity subscriptions; if we add entity event listeners, subscribe in `async_added_to_hass` and remove on teardown. Entry-owned ingestion subscriptions still require proper cleanup regardless of an entity-rule exemption.

**Our call, Silver:** apply `config-entry-unloading`, `docs-installation-parameters`, `entity-unavailable`, `integration-owner`, `log-when-unavailable`, `parallel-updates`, `reauthentication-flow`, and `test-coverage`. Apply `docs-configuration-parameters` when an options flow exists; otherwise document required/reconfigured fields under installation parameters and record the lack of optional parameters. `action-exceptions` is exempt without custom actions and becomes mandatory if a backfill action is added. [Test coverage](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/test-coverage/) is **above 95% for all integration modules**. Cloud polling, read-only sensors, and external statistics do not excuse availability, reauth, unload, or coverage requirements.

**Our call, higher tiers:** implement `devices`, `diagnostics`, `entity-device-class`, `entity-category` where suitable, `entity-translations`, `exception-translations`, `reconfiguration-flow`, and the Gold documentation rules `docs-data-update`, `docs-examples`, `docs-known-limitations`, `docs-supported-devices`, `docs-supported-functions`, `docs-troubleshooting`, and `docs-use-cases`. Redact diagnostics with `async_redact_data` and a tested secret/identifier inventory; never return raw portal payloads. Source: [diagnostics rule](https://developers.home-assistant.io/docs/core/integration-quality-scale/rules/diagnostics/). Adopt Platinum's `async-dependency`, `inject-websession`, and `strict-typing`: inject HA's shared async HTTP session into the client, never close that shared session, and keep typed boundaries.

**Our call, higher-tier conditions:** `discovery` and `discovery-update-info` are inapplicable without a supported discovery mechanism. `dynamic-devices` and `stale-devices` become relevant to account enumeration and meter replacement; do not label them irrelevant merely because the current account has one meter. `entity-disabled-by-default` depends on whether we add noisy/nonessential entities; `icon-translations` is unnecessary if device-class icons suffice. `repair-issues` applies when persistent problems need human intervention; ordinary temporary outages belong in coordinator error handling, and expired credentials belong in reauth. No Quality Scale rule proves tariff correctness, historic sum continuity, DST handling, or idempotent recorder writes. Those remain explicit project tests.

## Manifest, translations, and distribution

**Core says:** a custom integration needs a manifest `version` and declares exact external package requirements, its config-flow support, IoT class, and integration dependencies. `dependencies` means integrations that must be set up first, not pip packages. Sources: [manifest specification](https://developers.home-assistant.io/docs/creating_integration_manifest/) and [component checklist](https://developers.home-assistant.io/docs/creating_component_code_review/).

**Our call:** declare `domain: "nisc_smarthub"`, `name: "NISC SmartHub"`, `config_flow: true`, `integration_type: "service"`, `iot_class: "cloud_polling"`, `dependencies: ["recorder"]`, actual GitHub code owners, public documentation and issue URLs, and the release version. Use `requirements: []` only if there are no additional packages; otherwise pin each actual runtime library. Do not put Home Assistant itself in integration requirements. Omit a claimed Gold/Platinum `quality_scale`. The recorder dependency follows our mandatory statistics-writing behavior and [Opower's manifest](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/opower/manifest.json), not a universal HACS requirement.

**Core says:** custom integration translations are loaded from `translations/<language>.json`; unlike Core integrations, custom integrations do not receive the same automatic translation pipeline. Core's tests load `translations/en.json`, not `strings.json`. Sources: [custom localization](https://developers.home-assistant.io/docs/internationalization/custom_integration/) and [Core AGENTS.md](https://github.com/home-assistant/core/blob/2026.9.1/AGENTS.md). **Our call:** keep `strings.json` as the authoring source and ship resolved English JSON in `translations/en.json`, checking them together. Do not copy Core's `script.translations` command into this standalone repository and assume the Core checkout scripts exist here.

**HACS says:** the repository must be public, with a README and root `hacs.json`. Its [integration requirements](https://hacs.xyz/docs/publish/integration/) require domain, documentation, issue tracker, code owners, name, and version in the integration manifest; brand assets can live in the integration's `brand/` directory with at least `icon.png`. Its [general publishing requirements](https://hacs.xyz/docs/publish/start/) define `name`, `homeassistant`, `content_in_root`, `zip_release`, `filename`, and release selection. **Our call:** begin with `hacs.json` containing `{"name": "NISC SmartHub", "homeassistant": "2026.9.0"}`. Keep the standard `custom_components/nisc_smarthub/` layout, so `content_in_root` is unnecessary. HACS's minimum HA version is separate from the exact development pin.

**HACS says:** users add a repository URL with type **Integration** through [Custom repositories](https://hacs.xyz/docs/faq/custom_repositories/); default-store inclusion is a separate process. GitHub **releases**, not bare tags alone, supply the release version. `zip_release: true` requires `filename` and an uploaded matching archive asset. Sources: [publishing](https://hacs.xyz/docs/publish/start/) and [integration repository layout](https://hacs.xyz/docs/publish/integration/). **Our call:** start with normal repository downloads, publish a GitHub release whose tag matches the manifest version, and validate the installed integration from that release locally. Only enable `zip_release` if a build produces files absent from the source tree; then verify the archive's internal layout against the installed HACS version and test the asset, not merely the checkout. The fetched HACS pages verify the flag and filename contract, but did not establish the archive's internal directory layout, so that remains unverified. HACS installation and HA restart remain final local release checks before the separate production cutover.

## Concrete mise and uv development loop

**Verified package evidence:** [PyPI homeassistant 2026.9.1 JSON](https://pypi.org/pypi/homeassistant/2026.9.1/json) declares `Requires-Python: >=3.14.2`. [PyPI pytest-homeassistant-custom-component 0.13.364 JSON](https://pypi.org/pypi/pytest-homeassistant-custom-component/0.13.364/json) declares the exact dependency `homeassistant==2026.9.1`, plus `pytest==9.0.3` and `syrupy==6.0.0`. These metadata were fetched directly and parsed, not inferred from similar version numbers. The [plugin README](https://github.com/MatthewFlamm/pytest-homeassistant-custom-component/blob/master/README.md) says it regenerates against published HA releases, including betas; patch releases track automatic HA updates and minor releases track extraction changes. Its package version is not HA's calendar version.

**Our call:** add these exact entries to the existing `[dependency-groups].dev` array when implementation begins, retaining the existing lint/type-check tools:

```toml
"homeassistant==2026.9.1",
"pytest-homeassistant-custom-component==0.13.364",
```

The current `pytest>=9.0.2` constraint permits the plugin's exact 9.0.3 pin. Python must resolve to **3.14.2 or later within 3.14**, not just any 3.14 interpreter. Lock HA and its pytest plugin together when upgrading; do not let an independent plugin bump silently choose a newer HA. This recommendation does not establish that the entire current strict-warning test suite or macOS installation succeeds: neither installation nor tests were run for this research. Core's [CLI source](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/__main__.py) accepts Darwin and Linux; that is a development capability, not a recommendation to deploy production Core on macOS.

**Our call:** once those dependencies and the integration exist, run from the repo root:

```sh
mise exec -- uv sync --dev
mkdir -p config
ln -s ../custom_components config/custom_components
mise exec -- uv run --no-sync hass --config "$PWD/config" --script ensure_config
mise exec -- uv run --no-sync hass --config "$PWD/config" --debug
```

The symlink command is a one-time operation. A future mise task should create it only when absent, accept exactly the intended existing link, and fail on a conflicting directory/link rather than overwrite it. Keep `config/` ignored, including its database, logs, credentials, and `.storage`. Bind local HTTP to loopback by setting `http.server_host: 127.0.0.1` in `config/configuration.yaml` before onboarding; the CLI has no `--host` flag. Use a distinct configured port if 8123 is occupied. The [HTTP component source](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/http/__init__.py) is the configuration authority.

**Core says:** `-c` and `--config` are aliases; `--debug` enables debug mode; `--verbose` enables verbose file logging; `--open-ui` explicitly opens a browser and is not needed for agents. `--skip-pip` skips installation of required packages, while `--skip-pip-packages` accepts comma-separated package names; those two switches are mutually exclusive. The default log is `CONFIG/home-assistant.log`. Sources: [2026.9.1 CLI argument parser](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/__main__.py) and [ensure_config script](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/scripts/ensure_config.py). These flags were verified in source; `hass --help` was not executed because that would require the forbidden installation.

**Our call:** do **not** add `--skip-pip` to the initial run. Installing HA and the test plugin does not install every requirement of every enabled integration, including the frontend and generated default configuration. HA's manifest-driven installation can resolve those on startup. For a fully locked, installation-free loop, first inventory and declare the additional dependencies of the chosen local configuration in uv, then use `mise exec -- uv run --no-sync hass -c "$PWD/config" --debug --skip-pip`. That dependency closure is not verified here and must not be implied by the two pins above. HA-managed dependencies can also be removed by later uv synchronization if they were installed into the project environment rather than separately; uv ownership needs an explicit implementation decision before claiming hermetic runs.

The [integration blueprint's develop script](https://github.com/ludeeus/integration_blueprint/blob/master/scripts/develop) conventionally runs `hass --config "${PWD}/config" --debug` and creates configuration with `--script ensure_config`; it uses `PYTHONPATH` rather than a symlink. **Our call:** use the symlink instead, so the filesystem matches HA's normal `config/custom_components` discovery without shell import-path assumptions. The [HA loader](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/loader.py) loads the `custom_components` package and scans its paths. A checkout physically inside `config/custom_components/nisc_smarthub` also works but conflicts with this repository's HACS-ready root layout; do not relocate the checkout there. Restart the local process after Python changes because entry reload does not guarantee imported Python modules are reloaded. Reload entries to test lifecycle behavior, not as a substitute for restarting changed code.

## Browserless inspection and token bootstrap

**Core says:** the [REST API](https://developers.home-assistant.io/docs/api/rest/) accepts `Authorization: Bearer TOKEN`; `GET /api/states`, `/api/config`, and `/api/error_log` support inspection. The [WebSocket API](https://developers.home-assistant.io/docs/api/websocket/) connects at `/api/websocket`, sends `auth_required`, accepts `{"type":"auth","access_token":"..."}`, and returns `auth_ok`; authenticated clients can send `get_states` or subscribe to `state_changed`. Long-lived tokens can be created from an authenticated WebSocket connection with [the documented auth command](https://developers.home-assistant.io/docs/auth_api/#long-lived-access-token):

```json
{"id": 1, "type": "auth/long_lived_access_token", "client_name": "nisc-smarthub-local-agent", "lifespan": 365}
```

The lifespan is in days. Save the returned token securely; HA does not retain the token string for later retrieval. **Our call:** complete local onboarding once, use a local-only credential/token kept outside the repo, and inspect with:

```sh
curl --fail --silent --show-error \
  -H "Authorization: Bearer $HA_LOCAL_TOKEN" \
  http://127.0.0.1:8123/api/states
```

Never echo the token, enable shell tracing around it, or upload full state/diagnostic output without redaction. The state machine only proves entities, not external statistics. For those use the recorder WebSocket commands in [2026.9.1 recorder/websocket_api.py](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/recorder/websocket_api.py), including `recorder/list_statistic_ids` and `recorder/statistics_during_period`, with our `nisc_smarthub:` IDs, and verify units, hourly timestamps, sums, and repeat-import behavior.

**Noninteractive minting is possible, but not unauthenticated minting.** The documented long-lived-token command requires an already authenticated user. The [OAuth token endpoint](https://developers.home-assistant.io/docs/auth_api/) exchanges an authorization code or refresh token for an access token; it is not a password-grant CLI. Source inspection of [2026.9.1 onboarding/views.py](https://github.com/home-assistant/core/blob/2026.9.1/homeassistant/components/onboarding/views.py) shows that a fresh local instance can receive `POST /api/onboarding/users` with `name`, `username`, `password`, `client_id`, and `language`, create its owner, and return `auth_code`. Exchange that at `/auth/token` with `grant_type=authorization_code`, the same `client_id`, and `code`, then authenticate WebSocket and mint the long-lived token. The remaining onboarding endpoints include `core_config`, `analytics`, and `integration`; use the source-defined schemas and onboarding status rather than overwriting `.storage`.

**Our call:** ordinary agent inspection uses a token after one-time user onboarding. Fully headless fresh-instance bootstrap is feasible via the frontend's onboarding API, but that bootstrap is an internal, version-pinned API recipe, not a documented stable authentication shortcut. Its end-to-end execution was not verified here. There is no verified supported `hass` flag that prints an owner token or bypasses authentication. Never use a production token against the development instance or automate creation of another production owner.

## Testing and proof required at implementation

**Core says:** use HA fixtures and `MockConfigEntry`; annotate test arguments; prefer `@pytest.mark.usefixtures` for unused fixtures; split branches or parametrize them with named `pytest.param` cases; use Syrupy `.ambr` snapshots instead of giant repeated expectation dictionaries. Sources: [Core AGENTS.md](https://github.com/home-assistant/core/blob/2026.9.1/AGENTS.md) and [testing guide](https://developers.home-assistant.io/docs/development_testing/). The [custom-component plugin README](https://github.com/MatthewFlamm/pytest-homeassistant-custom-component/blob/master/README.md) changes the helper import to `pytest_homeassistant_custom_component.common`, requires `enable_custom_integrations` and `asyncio_mode = "auto"`, and documents the HA Syrupy snapshot extension plus colocated fixtures. Some recorder fixtures must initialize before custom integrations are enabled; encode fixture dependencies instead of trusting argument ordering.
